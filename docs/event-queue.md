# Event queue design

Once an employee starts an event from the booth screen, the screen shows a QR
code. Attendees scan it, enter name, title and email on their phone, and join a
queue. When a flight ends, the screen calls the next person, who gets 20 seconds
to press Enter or Space at the booth. If nobody presses, the screen removes them
and calls the next person. People are only called while the screen is open,
because the screen drives the calling.

Podpocalypse owns the queue, the turns, and its list of opened events. The event
tracker (`events.tmprl-demo.cloud`) only stores the event and its responses, and
knows nothing about the game. Podpocalypse calls it through generic Nexus
operations ([tracker contract](#event-tracker-contract)).

## What the people at the booth see

**Employee, no event open.** The open booth form works as it does today. A
signed-in `temporal.io` employee also sees **Start an event** with one field,
the title. Starting it creates the event in the tracker and opens
`/event/<booth-event-id>` on this screen. Employees also see the events this app
has opened, so a reloaded or replaced screen can reattach to one.

**Booth screen, event open.** There is one screen per event. The bottom-left
corner holds a panel that takes up as little room as possible:

- the QR code, which points at `/join/<booth-event-id>`;
- **Up next: Ada L. · press Enter or Space · 17**, with a countdown, when someone
  is being called;
- the next two or three names in the queue.

The panel stays in place during a flight. The ship flies to the right, and the
standings sit in the bottom-right corner, so the left side is the only free
space. When the queue is empty and nobody is flying, the QR code is shown large.

**Phone, `/join/<booth-event-id>`.** A form with name, title, and email, and no
consent checkbox: scanning the code and entering your details is the consent.
After joining, the phone shows the person's position and a rough wait ("You're
#3, about 4 minutes"), then **You're up: press Enter or Space at the booth** when
they are called. If their 20 seconds run out, it shows **You missed your turn**
with a button to join again.

**Flying.** Enter, Space, and the up arrow all flap. The key press that starts a
turn doesn't also flap.

## The queue rules

- A person can be in the queue once. A second join with the same email, or from
  the same browser, while they are waiting, being called, or flying returns
  their current place and doesn't add an entry.
- Once their flight ends, they can join again, at the back.
- If they are called and nobody presses Enter or Space within 20 seconds, the
  screen removes their entry and calls the next person.
- Nobody is called while the screen is closed. People keep joining, and the
  queue waits.
- Joining any number of times leaves one response in the tracker (see
  [Join](#join)).

These rules are against mistakes, not against someone trying to cheat. This is
an in-person work event. A browser ID is a random value the phone keeps in
`localStorage`. It catches someone joining again under a different email, and
it is not a security control.

## Workflows

The control Worker (`podpocalypse-control`, the one we don't kill) runs all of
these.

### `BoothEventWorkflow` (`booth-event/<id>`)

One per event this app opened. `<id>` is generated by Podpocalypse, because the
tracker picks its own event ID (the slug) during creation. The workflow holds:

- the tracker event ID, name, and link;
- the queue, in order: player ID (the existing email hash), display name, title,
  email, and browser ID;
- the current turn: `idle`, `calling` (an entry), or `flying` (an entry and a
  session ID).

The workflow has no timer of its own. The screen drives each turn through three
Updates, and the workflow keeps the order and the rules:

| Name | Kind | What it does |
| --- | --- | --- |
| `open` | Update, sent with the start (Update-with-Start) | Calls Nexus `create_event` with Podpocalypse's default event, then stores the tracker event. |
| `join` | Update | Checks the person isn't already queued, calls Nexus `submit_participant`, appends them, and returns their ticket and position. |
| `call_next` | Update | Rejected while `flying`. While `calling`, returns the entry already called, so a reloaded screen picks up where it left off. While `idle`, marks the head of the queue `calling` and returns it, or returns nothing when the queue is empty. |
| `start_turn` | Update, with the entry ID | Accepted only while that entry is `calling`. Starts `GameRunWorkflow` as a child and returns the session ID once the child has started. |
| `skip` | Update, with the entry ID | Accepted only while that entry is `calling`. Removes it and sets `idle`. |
| `state` | Query | The screen and phone view. Browsers never send it directly ([Reads](#reads)). |
| `close` | Update | An employee closes the event at the booth; the workflow finishes once the current flight ends. |

`start_turn` and `skip` name the entry, so a late `skip` from a stale tab
can't remove the person who was called after them. When the child completes, the
workflow removes that entry, which lets the person join again, and sets `idle`.
It doesn't call anyone next; the screen does.

The screen's loop:

1. With no flight running, send `call_next`. If it returns nobody, wait for the
   next poll to show someone queued and send it again.
2. Show **Up next** and count down 20 seconds in the browser.
3. Enter or Space sends `start_turn`, and the flight starts. When the countdown
   runs out, send `skip` and go to 1.
4. When the flight's result screen ends, go to 1.

Because the countdown runs in the browser, closing the screen stops calling. If
the screen closes during a call, that person stays `calling` until a screen opens
again. `call_next` then returns them, with a fresh 20 seconds.

Continue-As-New only between turns, when Temporal suggests it. The queue and the
event details carry over as input. The child uses
`ParentClosePolicy: ABANDON`, so nothing about the parent's run can end a flight.

`join` calls Nexus and then appends. Two joins for the same person can both pass
the check before either call returns, so the handler checks again after the call
and returns the existing entry if one appeared meanwhile.

### `GameRunWorkflow`, `GameSessionWorkflow`, `PlayerWorkflow`

These stay as they are. For an event, `GameRunWorkflow` starts as a child of
`BoothEventWorkflow` and records its score on `leaderboard/<booth-event-id>`. The
open booth keeps starting it from the API and recording to `leaderboard`.

### `LeaderboardWorkflow`

There is one per event (`leaderboard/<booth-event-id>`), plus the existing global
`leaderboard` for the open booth. `GET /api/leaderboard?event=<id>` and the prize
route take the event. New workflow IDs mean no running history has to replay the
change.

### Opened events

The list of events this app opened is a Visibility query:
`WorkflowType='BoothEventWorkflow' AND ExecutionStatus='Running'`, with the
event name in the memo. No extra workflow keeps a registry. After a catalog
namespace reset this list is empty, but the events and their responses are still
in the tracker.

## Flows

### Start an event

`POST /api/booth-events {name}`, employee only. The API sends Update-with-Start
to a new `booth-event/<id>` with the `open` Update. The `open` handler calls
Nexus `create_event` with:

- the title from the screen;
- an end date three days from today (UTC). Submissions close at 00:00 UTC after
  the end date, so "today" would close mid-afternoon at a US booth;
- a form with one section and three required questions, with IDs `name`, `role`
  ("Title"), and `email`. The tracker treats those IDs as its identity fields;
- `createdBy`, the employee's email;
- `requestId`, the booth event ID. A retried Nexus call returns the same event
  and doesn't create a second one.

These defaults are one Go function in this repo. Changing them never touches the
tracker. Name, end date, and questions can be edited afterwards in the tracker's
event editor.

### Join

`POST /api/booth-events/{id}/join {name, title, email, browserId}` sends the
`join` Update and returns `{ticket, position}`. The phone keeps the ticket, which
is the player ID and never the email.

The `submit_participant` request ID is a hash of event, email, name, and title.
The same details sent again hit the tracker's stored receipt and write nothing;
new details for the same email replace that participant's row. Either way the
tracker holds one response per person.

If the tracker rejects the submission, the phone says why: the event has ended,
or "This event's form changed; ask the booth staff" when someone added a
required question in the editor.

### Take a turn

Each step the screen takes is one request, which sends one Update:

- `POST /api/booth-events/{id}/next` sends `call_next` and returns the called
  entry's ID and display name, or nobody.
- `POST /api/booth-events/{id}/turn {entryId}` sends `start_turn`, then waits for
  the session to be playing, as `/api/play` does today, and the flight starts.
- `POST /api/booth-events/{id}/skip {entryId}` sends `skip`.

Only the booth screen sends these. They need no employee sign-in, since the
screen is a public page at the booth.

### Reads

The screen and every phone poll `GET /api/booth-events/{id}` (with `?ticket=`
from a phone). The API answers from one `state` Query per event per second,
cached in the process, so a room full of phones doesn't send a room full of
Queries. The phone gets its own position and the screen's public view, with
names shortened to first name and last initial. Emails are never returned.

## Removed

- `KioskWorkflow`, `/api/kiosk/bind`, `boothState`, and `ensureKiosk`. Terminate
  the running `kiosk` workflow after the deploy.
- The flight code: the `#code` field, `PlayRequest.FlightCode`, `ClaimFlight`,
  `writeFlightErr`.
- `ListLeadEvents`, `GetLeadEvent`, and the per-request `lead-get-*` and
  `lead-list-*` workflows. The booth reads event details from its own
  `BoothEventWorkflow`.
- The consent checkbox, `PlayRequest.Consent`, and the consent check on
  `/api/prize`. `PlayerState.Consent` stays in the struct so running player
  histories decode unchanged; nothing reads it.

## QR code

The QR points at Podpocalypse, so the tracker's `qr.png` doesn't fit. Copy the
tracker's dependency-free `internal/qrcode` package (same owner, same license)
and serve `GET /api/booth-events/{id}/qr.png`.

## Rollout

The control Worker is unversioned. `BoothEventWorkflow` and the per-event
leaderboards are new types or new IDs. Changes to `GameRunWorkflow`, such as the
leaderboard ID taking the event, apply to runs that start after the deploy; a
run in flight during the deploy replays. Keep the added code after the existing
commands, or deploy with no flight running. Deploy the tracker's `create_event`
before this.

## Event tracker contract

Endpoint `event-leads-participants`, service `event-leads`. The tracker's
`DemoProject` keeps `allowedCallerProjects: [podpocalypse]`. The registry only
lets the handler's project declare an endpoint, and we are not changing the
registry. All operations are synchronous, so each must answer within Nexus's
10-second limit.

| Operation | Input | Output |
| --- | --- | --- |
| `create_event` | `requestId`, `name`, `description`, `endDate`, `form`, `createdBy` | the event: `id`, `link`, `name`, `status`, `closesAt` |
| `get_event` | `eventId` | the same |
| `submit_participant` | `eventId`, `submission` (`name`, `role`, `email`, `requestId`, `answers`) | `status` |

The tracker side is described in its `docs/nexus-api.md`.
